Benchmarks

Looksie 1.2.0, rules only (no AI). Measured 21 November 2026 on 202 merged pull requests from 34 open-source repositories in 11 languages.

The short version
  • We took real pull requests where a reviewer asked for something to be fixed and the author then changed that code, and ran Looksie on each pull request as it was when the reviewer first commented, before any fix.
  • Looksie's decisions held 75% of the files that needed fixing. Reading the same amount in random order finds 60%; biggest files first, 42%.
  • Reading in Looksie's order, the first 20% of a pull request already reaches 34% of them, against 22% in random order.
  • On pull requests over 5,000 lines, this version's decisions cover 63% of the change, down from 74%, for the same share of what needed fixing.

Where the misses were

Of 560 files that needed fixing, 418 were in a decision. Of the rest, 125 were quick looks, 17 were over the decision limit, and 0 were set aside as generated. Most quick-look misses are test-only and docs-only steps: reviewers often ask for tests to be fixed. We tried making those decisions too, and it meant reading most of every pull request, so we have not.

How it was measured

  • The pull requests: recently merged, 4 or more files and 150 or more changed lines, with at least one review comment that led to a change, from JetBrains/kotlin, PostHog/posthog, apache/airflow, apache/kafka, astral-sh/ruff, astral-sh/uv, bevyengine/bevy, denoland/deno, dotnet/aspnetcore, dotnet/efcore, dotnet/maui, dotnet/runtime, elastic/elasticsearch, elastic/kibana, getsentry/sentry, grafana/grafana, hashicorp/terraform, home-assistant/core, kubernetes/kubernetes, langchain-ai/langchain, laravel/framework, mastodon/mastodon, microsoft/PowerToys, microsoft/terminal, microsoft/vscode, n8n-io/n8n, pandas-dev/pandas, prometheus/prometheus, rails/rails, spring-projects/spring-boot, supabase/supabase, tokio-rs/tokio, vercel/next.js, zed-industries/zed. Many are over 2,000 lines. 16 of them were written by a coding agent.
  • What needed fixing: an inline review comment from a person (not a bot, and not the author) that GitHub later marked as outdated, meaning the code under it changed afterwards. Counted per file.
  • When: each pull request as it was at the commit its reviewer first commented on, so the fixes are not in what Looksie sees.
  • Looksie: the same engine as the app, from the command line, with no AI. A file counts if it is in a decision.
  • Baselines: for each pull request, files read in random order (averaged over 500 shuffles) or biggest first, stopping before they read more lines than Looksie's decisions cover.
  • Held out: the weights that weigh files were fitted on 21 of the 34 repositories and never on the other 13. This version's change to how decisions are chosen was developed on the 21; on the other 13 it made no measurable difference.

What this does not show

  • A comment can go out of date for other reasons, and reviewers do not comment on everything that deserves it. The answer key is a good signal, not the truth.
  • Only pull requests with at least one such comment are included, which leans towards pull requests where reviewers engaged.
  • It measures where to look, not whether a reviewer would spot the problem once there.
  • Few agent-written pull requests in big open-source repositories have human review comments yet, so the agent results rest on 16 pull requests.
  • For an earlier commit, GitHub lists at most 300 changed files, and CI results are from the final commit.

The scripts that collect the pull requests and score them, and the list of pull requests, are in the open-source repository. Found a pull request where Looksie got it wrong? Send it to us. See also how Looksie decides.
